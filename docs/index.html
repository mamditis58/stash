Working local experiment

Authentication playground

Authentication means checking who you are. This project lets you create a test account, log in, ask the server who you are, and log out.

The server checks a password when you log in. It then uses a temporary session to remember your login. A session is a record of a successful login. Accounts and sessions disappear when the server restarts.

Beginner guide / Login

Follow a login, one step at a time.

A request is a message from the browser to the server. A route is the address for one server task. The diagram below follows the routes in our local experiment. Read from top to bottom.

  1. 1
    Create a test account

    Browser → POST /api/register → server

    The browser sends an invented username and password. The server saves a password hash and a salt. A hash is a one-way result used to check a password. A salt is random data added before hashing.

  2. 2
    Log in

    Browser → POST /api/login → server → browser

    The server hashes the entered password with the saved salt. It compares the result with the saved hash. If they match, it creates a session and sends a random session token to the browser.

  3. 3
    Ask “Who am I?”

    Browser + cookie → GET /api/me → server → username

    A cookie is a small value saved by the browser. Our cookie holds the session token. The browser sends it with the request. The server checks that the session exists and has not expired. The session lasts 15 minutes.

  4. 4
    Log out

    Browser → POST /api/logout → server → expired cookie

    The server removes the session. It tells the browser to clear the cookie. The old token can no longer open the account route.

Where does each value go?

Password
Entered in the browser and sent to the local server. The server keeps a salt and hash in memory. It does not save the password as text.
Session token
The browser keeps the token in an HttpOnly cookie. HttpOnly prevents page JavaScript from reading it. The server keeps a hash of the token.
CSRF token
A separate value sent with logout. CSRF means cross-site request forgery. This check helps stop another site from making a logout request with your cookie.
Server memory
Temporary storage while the server runs. Restarting clears every account and session. This project has no database yet.

Use invented passwords. The experiment uses local HTTP, which does not encrypt traffic. It is a learning tool and is not ready for public login use.

Beginner guide / GitHub

How does a change reach this website?

A branch is a separate place to make changes. A commit saves a change. A pull request proposes that change for the shared version, called main. A merge adds the proposed change to that shared version.

  1. 1
    Edit on a branch

    Change one sentence in docs/index.html. Save a commit with a short message about the change.

  2. 2
    Open a pull request

    Read the difference in “Files changed.” Codex can review the proposal and report problems. You must also read the change yourself.

  3. 3
    Wait for four test results

    CI means continuous integration. GitHub Actions runs our automatic checks on Linux and Windows with Node.js 22 and 24. A failed check gives a log that explains what failed.

  4. 4
    Merge after checks and review

    Branch protection blocks direct changes to main. The four test jobs must pass. The branch must be current, and review conversations must be resolved. Codex review is a useful step, but is not itself a required status check.

  5. 5
    Publish with GitHub Pages

    The workflow tests main again. It then sends the docs/ files to GitHub Pages. Pages hosts this public website. It serves HTML and CSS, which define the page content and appearance.

A pull request runs tests without publishing this page. The page updates after a successful merge and deployment. Deployment means sending the website files to the hosting service.

Try it / One small change

Your first exercise: change one sentence.

Start with the portfolio. You can do this in GitHub's browser editor. You do not need a terminal for this exercise.

  1. Open the page source on GitHub.
  2. Click the pencil button. Find one sentence about what you are learning.
  3. Change the sentence. Keep the HTML tags around it. Tags such as <p> mark the start and end of a paragraph.
  4. Click “Commit changes.” Choose a new branch and start a pull request.
  5. Read “Files changed.” Wait for the four required tests. Read any Codex findings.
  6. Merge the pull request when the change is ready. Wait for the Pages deployment, then refresh this page.

Write down your prediction first: “After the deployment, my new sentence will appear.” Compare that prediction with the result.
